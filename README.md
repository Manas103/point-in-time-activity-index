# Point-in-Time Activity Index and Release Pack

A monthly weighted activity index, rebuilt from 85 simulated source series across four
categories, with a genuine vintage store that reproduces any published value exactly as it was
known on its own release date, a measured revision profile, a publish gate that refuses a stale
series, and a one-page Excel chart pack for a non-technical reader. Python 3.12, DuckDB, pandas,
openpyxl. Every number below was measured on this machine by running the real code, not targeted
in advance.

## Why this exists

The Chicago Fed publishes the CFNAI, a monthly weighted average of about 85 existing monthly
indicators across four categories (production and income, employment/unemployment/hours,
personal consumption and housing, and sales/orders/inventories), released with revisions to the
prior three months every time. This repository is a small, honest simulated version of that
shape: synthetic source series instead of real ones, an equal-weight combination instead of the
real index's PCA-derived weights, but the same genuine mechanics a published, revised index
actually needs: an append-only vintage store, a point-in-time reconstruction, and a release pack
a non-technical reader can act on without touching the database.

## Honest framing, up front

- **This is a simulated reproduction of the CFNAI's shape, not the real CFNAI.** All 85 source
  series, their values, and every vintage and revision are synthetic, generated by
  `activityindex/simulate.py` from a fixed seed. No real source data (Federal Reserve, BEA,
  BLS, or otherwise) is used anywhere in this repository.
- **The weighting is an honest simplification, not the real CFNAI's weighting.** The real CFNAI
  uses PCA-derived weights from a dynamic factor model; this index equal-weights the standardized
  (z-scored) value of every one of the 85 series. The category split here (22/21/21/21 across
  production, employment, consumption, sales) is deliberately even, not the real CFNAI's
  23/24/15/23 split, only the shape ("four categories, about 85 series total") is reproduced.
- **The staleness rule, the publication-lag ranges, and the revision-magnitude behavior are all
  invented for this project**, not drawn from any real statistical agency's actual release
  calendar or revision history.
- **Machine and toolchain.** 8 physical / 16 logical cores, Windows 11 Home, Python 3.12.10,
  pandas 3.0.6, DuckDB 1.5.6, numpy 2.5.3, openpyxl 3.1.5, pytest 9.1.1.

## Architecture

```
activityindex/
  config.py           seed, 128-month calendar (2016-01 to 2026-08), category/series-count
                       layout, staleness lookback, publication-lag ranges, min history months
  simulate.py         deterministic synthetic source series and their vintage histories
  vintage_store.py    the DuckDB append-only store: source_vintages, published_index, and the
                       point-in-time query (filter by vintage_date first, dedupe second)
  index_builder.py    z-score each series, equal-weight combine, publish without hindsight
  oracle.py           independent pure-Python recomputation (no pandas/duckdb), diffed exactly
                       against index_builder's fast path
  publish_gate.py     the staleness rule: evaluate() is pure logic over a plain dict, check()
                       is the DB-backed wrapper the release pipeline actually calls
  measurements.py     the five claim measurements, each returning a plain honest number
  excel_report.py     the one-page Excel chart pack builder
scripts/
  build_database.py   generates all 85 series' vintage histories and every historical release
  run_measurements.py runs all five measurements, prints JSON (docs/measurement_output.txt)
  build_excel.py      builds docs/activity_index_release_pack.xlsx from the built database
tests/
  test_vintage_store.py   point-in-time correctness, including the filter-before-dedup regression
  test_index_builder.py   equal-weight combination against a hand computation, lookahead guard
```

### Why the point-in-time query filters before it dedupes

`vintage_store.query_point_in_time` filters the raw, undeduped vintage log by
`vintage_date <= as_of` first, and only picks the highest `revision_number` per
`(series_id, reference_period)` from what survives that filter. Deduping first and filtering
second is the exact footgun the sibling repository `point-in-time-gas-backtest` hit: a later
revision's own `vintage_date` can be after `as_of` even though an earlier, visible revision of
the same row existed, so deduping first silently resurrects lookahead by picking a row that
should not have been visible yet. This repository inherits that discipline deliberately rather
than relearning it, and `test_filter_before_dedup_regression` pins the correct order with the
exact scenario that would expose the bug if the query were ever rewritten the wrong way around.

### Why the oracle only imports config.py

`oracle.py`'s pure-Python recomputation imports nothing from `index_builder.py` or
`vintage_store.py`, only the declared policy constants in `config.py`. A bug specific to the fast
path's SQL or pandas code has a real chance of showing up as a disagreement between the two
independent implementations; it has no chance of showing up at all if both paths share the
buggy code.

## Findings

**A real bug surfaced from a pandas 3.0 behavior change, not from the point-in-time logic
itself.** `query_point_in_time` compares `reference_period <= target_period` after pulling dates
back from DuckDB with `fetchdf()`. Older pandas silently coerced DuckDB's `DATE` columns
(returned as `datetime64[us]`) against plain `datetime.date` values in a comparison; pandas
3.0.6, the version actually installed here, raises `TypeError` instead. The fix normalizes both
date columns with `.dt.date` immediately after `fetchdf()`, once, right where the DuckDB result
enters the rest of the pipeline, so every downstream comparison works against plain
`datetime.date` values the same way `config.py`'s own calendar functions do. The measurement
that discriminated the cause from a logic bug: the error was a `TypeError` on the comparison
itself, not a wrong value, and it disappeared identically for every query once the dtype was
normalized, which pointed at a type mismatch introduced between library versions, not a flaw in
the filter-then-dedupe ordering.

## Sibling comparison

The nearest existing repository is
[`point-in-time-gas-backtest`](https://github.com/Manas103/point-in-time-gas-backtest) (Python,
pandas, DuckDB, numpy), which has a genuine vintage store that reveals only what was known as of
each trading session, and an independent reference oracle diffed against its fast DuckDB path,
the same two disciplines this repository reuses deliberately (see "Why the point-in-time query
filters before it dedupes" above). That repository's deliverable is a trading-rule backtest,
walk-forward over restated data versus point-in-time data, measuring a look-ahead overstatement
in a Sharpe ratio. This repository's deliverable is a published index with a measured revision
profile and a release pack, a different artifact built on the same vintage-store technique, which
is why this project is a new repository rather than an extension of that one.

## Limitations

The source data, every vintage, and every revision are synthetic (see "Honest framing"). The
weighting is an honest equal-weight simplification of the real CFNAI's PCA-derived weights. The
staleness rule, publication-lag ranges, and revision magnitudes are invented for this project,
not drawn from any real statistical agency's actual release calendar. The revision profile
(claim 3) is a descriptive measurement, not a pass/fail target, by the claim's own wording; there
is no "correct" revision magnitude to compare it against since the underlying revision process is
itself synthetic.
